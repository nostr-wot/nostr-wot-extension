## 1. Why it feels like it fails sometimes

The owner's phrase is accurate: almost nothing here is broken always. The popup's behavior depends on four hidden inputs — is the service worker warm, is the vault's startup unlock settled, is the current tab a connected site, did the last RPC succeed — and the UI renders a confident answer in every combination, including the ones where it doesn't know. Ranked by how often a real user hits each:

**1. Never-lock vaults open to a locked popup after every cold start.** Trigger: auto-lock set to Never, worker idle >30s (routine), open the popup. `vault_isLocked` answers `vault.isLocked()` directly (lib/bg/vault-handlers.ts:101) without awaiting `whenStartupUnlockSettled()` — the helper built for exactly this (lib/vault.ts:403, documented "request paths await this") — so the RPC races the startup auto-unlock's PBKDF2 and wins. The successful unlock then writes nothing the popup watches (only `lock()` writes `LOCK_STATE_KEY`, vault.ts:364), so the answer never corrects. What the user sees: the wallet balance card and Wallet menu row (`vault.locked` gate at MenuOverlay.tsx:217, HomeTab.tsx:198) and every locked-gated action vanish for that popup's entire life, then reappear on the next open for no visible reason. This is the extension's most reproducible "sometimes." Fix: `vault_isLocked` awaits the settle gate; startup unlock writes `LOCK_STATE_KEY` on success. Two lines, both node-testable today.

**2. The home screen is hostage to site state.** Trigger: open the popup on a new tab, a chrome:// page, or any not-yet-connected site — daily. HomeTab's empty/loading/notConnected branches return early (HomeTab.tsx:276, :292, :307) before the pending-requests card (:330), the wallet card, and the whole Account group render. Mutes and Recent activity have no other entry point in the product (PopupApp.tsx:117-119 are their only openers), so on a new tab they are unreachable anywhere. Worse, pending signing requests queued from another tab are invisible in exactly these states — and even in the connected state the badge counts all origins (HomeTab.tsx:206-209) while the approval overlay correctly fail-closes to the current domain (ApprovalOverlay.tsx:101-103), so the card shows a count with no list and no action; the request dies at the ~2-minute timeout. What the user sees: "sometimes my stuff is there, sometimes the popup is one empty card." Fix: the site state becomes one card among others; pending, wallet, and Account render whenever an account exists, and the pending card gains an action.

**3. Unlock feels hung on every cold unlock.** UnlockModal's destructure omits `loading` (UnlockModal.tsx:50 — the hook exposes and sets it; grep confirms `loading` appears nowhere in the file), so for the 1–3s of PBKDF2-plus-cold-wake nothing on screen changes; Enter can fire a second `vault_unlock` mid-flight, and a wrong password then double-counts against the persisted lockout guard (vault-handlers.ts:51-62). The single most-used gate in the product reads as dead. Fix: destructure `loading`, disable inputs, swap the button label (the in-repo pattern exists at KeyActionModal's `ncGenerating`).

**4. Cold-worker failures are painted as facts.** One family, many surfaces, all "failing sometimes" on a slow machine or dead worker: a failed `wallet_hasConfig` renders the wallet **setup screen** over a configured wallet (WalletSection.tsx:22-24 `catch { setConfigType(false) }` — the corrected pattern sits three files away in useWalletBanner); `pqc_checkPublished`'s relay catch returns `{published:false}` (lib/bg/pqc-handlers.ts:291), so the home card says "Set up post-quantum keys" and PqcSection offers Publish to a user whose attestation is live; FiltersModal's catch fabricates an editable **empty mute list** (FiltersModal.tsx:88-90) whose Publish then wipes the real kind:10000 including private mutes — and it is worse than the catch, because `fetchMuteList` resolves a zeroed list through the *success* path when all relays time out (8s), so only a background-side "reachable" flag can fix it; ActivityModal shows "No activity yet" while loading and forever after a failed read (no catch, no loading flag); the tx list shows "No transactions yet" on a failed fetch with no retry (Wallet.tsx:220); PasswordStep's probe catch renders "create a new vault" over an existing one (PasswordStep.tsx:51-52). Fix per surface is small and patterned: null = unknown, error state with Retry; background error markers for the two relay reads.

**5. Silent lost clicks.** The shipped class R1 was meant to end, alive on specific surfaces: home-card Connect has try/finally with no catch (HomeTab.tsx:234-241 — the globe twin was fixed in d18d127); "Not now"/"Never" run `window.close()` in a finally, so a failed dismissal is indistinguishable from success and the site re-prompts a user who said Never (HomeTab.tsx:250-257); the identity toggle flips optimistically with no revert — a privacy control lying until reload (:225-228); both NIP-46 cancel paths bypass `runAction` (ApprovalOverlay.tsx:354-359, :394-399) on the one request type whose failure mode is "remote signer never answers"; KeyActionModal's reveals end in `catch { /* ignore */ }` and its three key-material copies are un-awaited, feedback-free `clipboard.writeText` calls (:117-119, :137-139, :158-160) — the only silent copies among ~11 sites, on exactly the values the user cannot visually verify; PQC key removal gates on native `confirm()` (PqcSection.tsx:219), which some popup contexts suppress → a Remove button that sometimes does nothing, on a shipping Safari target.

**6. The money flows are destroyed by using them.** Deposit: every piece of state is `useState` (Wallet.tsx:91-98, zero `storage.session` writes in the file), so switching to a wallet app to pay — the flow's entire purpose — destroys invoice, payment hash, and paid-detection; a backdrop click discards a payable invoice with no confirmation (:645), and because the backdrop uses `onClick` rather than Modal's documented `onMouseDown` pattern (Modal.tsx:56-59), drag-selecting the bolt11 and releasing outside the card closes it too; the QR has no expiry state and polls a dead invoice indefinitely. Send: `intentId` is minted per click (:337) and guards only transport retries; the mount surfaces no in-flight record (:228-234), so the canonical MV3 gesture — Pay, popup dies on focus switch, reopen to an unchanged balance, Pay again — is a second real payment.

**7. Wallet dialogs paint over the approval sheet and the lock screen.** Five dialogs portal to `#root` at z 500 (Wallet.tsx:644, :706, :844, :1046; PermissionsSection.tsx:289; Wallet.module.css:210/:445, Settings.module.css:254) while every consent surface lives inside `.card`, a stacking context at z 1 (PopupApp.module.css:29-31) — so the approval sheet (500/501) and even the lock screen's 9999 are structurally underneath. Since 39156dd pushes lock state live, auto-lock now visibly fires *under* an open send dialog: the dialog stays interactive, wallet RPCs fail vault-gated with no explanation, and an arriving signing request times out unseen. Root cause found this round: `sectionSlideIn 0.2s ease-out both` (MenuOverlay.module.css:15) retains an identity transform forever, turning `.sectionContent` into the containing block for `position:fixed` — that is *why* the dialogs fled to `#root`, and the non-portaled wallet settings overlay is the live victim (its "full-page" `inset:0` covers only the section body). Rarer than items 1–6, but the worst class: a key-custody extension whose consent surfaces lose the paint order to a deposit QR.

**8. The add-account wizard's tail: five popup opens can destroy the vault.** PasswordStep probes `vault_unlock('')` on *any* locked vault, not just never-lock ones (PasswordStep.tsx:39-43); each failed probe increments the persisted guard (vault-handlers.ts:73-76). An abandoned wizard re-mounts that step on every popup open — the persist effect renews its own 5-minute TTL on each open (useWizardFlow.ts:86-93), so abandonment never expires. Five opens = lockout with zero passwords typed; on the sixth the guard *throws* (vault-handlers.ts:69-71), the catch maps any throw to `vaultExists=false` (PasswordStep.tsx:51-52), the wizard renders "Protect your keys" as if no vault existed, and completing it calls `onboarding_createVault` — which has **no existence guard** (onboarding-handlers.ts:702-717) and `vault.create()` overwrites the blob with only the new account. Every stored private key is gone while the accounts list still shows the old accounts. Same mount effect, different arm: with an unlocked vault, the abandoned account is silently added with no click (:46-50). Low frequency, catastrophic severity, and three small fixes de-arm it entirely.

**9. Deterministic embarrassments that read as "broken."** The Done screen prints literal `wizard.type.nsec` / `wizard.type.npub` for every key importer in all six locales — the AccountType union was renamed and no locale (en included) has the new keys (DoneStep.tsx:34; lib/types.ts:26; verified by script). The Lightning-address consent dialog drops `{address}` in de/es/fr/it/pt (15 placeholder drops total, re-verified: 3 keys × 5 locales) — a publish-consent prompt that never names what it publishes. The PQC "How it works" button has never rendered: OverlayPanel's centered branch (taken whenever `onBack` is passed, which MenuOverlay always does — OverlayPanel.tsx:32, :41-58) silently drops `headerRight`, and `styles.headerHelp` has no CSS definition anywhere — so the explainer for the headline feature is one-shot per install. InfoTooltip's bubble is transparent (`var(--bg-card)` undefined, InfoTooltip.module.css:18 — theme.css defines `--card-bg`, a different name), so the only in-place explanations of Relays and Mutes are unreadable text soup. Security/PQC/Network settings sections clip below the fold with no scrollbar (no overflow rule anywhere in the OverlayPanel → menuContent → sectionContent → section chain; only Wallet's section self-scrolls).

**10. Stale in-session cards.** Publish the PQC attestation, close the menu: the home card still says "Set up" (PqcCard's effect has `[]` deps, no invalidation — the exact wrong-state invitation its docblock says it prevents). Edit mutes: the count keeps its mount value. Publish a profile edit: the top bar keeps the old name/avatar for the session, because the background writes `profile_<pubkey>` while AccountContext watches only the legacy `profileCache` aggregate (profile-handlers.ts:239-244 vs AccountContext.tsx:61, :117).

```
│   └── Account group: Edit profile · Mutes → FiltersModal · Relays → menu:network · Post-quantum → menu:pqc
│       (empty/loading/notConnected: one connect/empty card replaces all of the above)

    Network [relay editor] · footer [language, version]

```

**The structure is broadly right at the box level, and that is a finding.** Connected-site everyday actions are 0–2 taps; dangerous actions (nsec export) sit appropriately deep behind warnings; the wizard's ~7 create screens are standard custody onboarding; approval's detail-first two-tap flow is correct consent posture. What is wrong is not where the boxes are but the **gates** (home hostage to site state), the **duplications** (two permissions hosts, three dialog systems, two stacking universes, two profile-cache schemas), the **edges** (labels that contradict destinations and state), and one **dropped box** (NIP-46 management deleted without re-homing). Inventing a new hierarchy would churn learned habits to fix problems that live in the seams.

### Proposed moves, each with justification and cost

1. **Home stops gating on site state.** Pending card, wallet card, and the Account group render whenever an account exists; the site slot varies (connected controls, connect offer, or a "no site here" notice). Justification: the single largest "works sometimes" driver; mutes and activity gain their only site-independent route; pending requests become visible in the states where the origin-filtered sheet correctly won't show. Cost: a ~40-line restructure of one file's return (the hooks already compute everything), but the **hardest verification in this report** — four site states × account states × German, by eye, no test seam. Habit risk: none; nothing moves, things stop disappearing.
2. **One permissions host.** Immediately: pass the already-captured `initialDomain` (one attribute — PopupApp.tsx:163-172 currently gates on `permsDomain` then discards it, while PermissionsSection.tsx:42-51 honors the prop). Then fold the bare PopupApp host into the menu deep-link (`setMenuSection('site-permissions')` + a domain param), the pattern onOpenPqc/onOpenWallet already use. Justification: today the same section has two shells with different titles and back semantics, and the more prominent one is broken. Cost: one line now; ~25 net-negative lines later; habit risk none (the section itself is unchanged).
3. **Site card becomes the site-control center.** Add Disconnect beside the identity toggle (the action currently lives only in the globe popover) and the connect-failure line the globe already has. Justification: state and its reverse action on the same surface; kills the two-surfaces-disagree class inside one 380px window. Cost: small; the globe stays as a mirror with identical strings.
4. **Menu edges.** Rename "Network" → "Relays" (the home row already taught the name; key exists), give the wallet row a state-neutral description ("Balance, deposits, and payments" — today it permanently reads "Connect a Lightning wallet"), reuse the PQC card's plain phrasing in the menu, and add a "Remote signer" row (gated on isNip46) under Security — all six locales already carry every string and `nip46_revokeSession` is registered and uncalled. Cost: locale edits ×6 plus one small section; the only habit broken is the "Network" label, mitigated by the home row.
5. **One stacking universe** (the structural precondition, round-2 R9's still-open decision — now with a concrete resolution): fix the retained transform (`backwards`, 1 line), then bring the five portaled dialogs back inside `.card` (or a single layer host as its last child), and write the z-order as theme tokens: lock screen > approval sheet > non-fullScreen unlock above the sheet's scrim tier > dialogs > dropdown (400) > panel (300) > content. Justification: consent surfaces must win by construction, not by DOM accident; every future portal currently inherits the inversion. Cost: ~a day; one dialog per commit; the 5×2 manual matrix.
6. **Finish the OverlayPanel contract**: `footer` slot first, `headerRight` in the centered branch (+ author `.headerHelp`), then opt-in `scroll` keyed off `currentSection` (the sections share one panel, so "one section per commit" means toggling per section), deleting each consumer's private scroll wrapper in the same commit; adopt Wallet's `.section` semantics as the single contract. Justification: seven consumers re-solve scrolling at seven depths, three clip today, and the last one-shot attempt was reverted for exactly the regressions the footer slot prevents. Cost: ~2 days across ~9 commits, each one surface, each eye-verified; plus the two execution caveats a naive migration gets wrong (scrollbar inset from `.overlay`'s 16px padding; shadow headroom inside the root list's scroller).
7. **Wallet decomposition** (DepositModal, SendModal, TransactionsCard, wallet settings on OverlayPanel with a real title), with deposit/send session snapshots and the in-flight banner as the point of the split, and the dialogs landing on shared Modal so Escape/focus/scrim come along. Justification: three of the worst money findings live in one 1068-line closure; the popup's destroy-on-blur lifecycle makes session persistence a correctness feature. Cost: the 3–4 day plan-step-9 shape, after the stacking decision.
8. **Decide the two dead surfaces.** `src/onboarding/` and `src/prompt/` are built as entries and referenced by nothing; they carry ~75 locale keys ×6 and have already drifted from the live wizard and cost one audit a false lead. Verify nothing external links their dist paths, then delete — or deliberately wire prompt as the no-`action.openPopup` fallback. Keeping dead parallel consent UI pending a maybe is the worst option.
9. **Explicitly not moving:** the wizard's step order, the approval sheet's detail-first flow (and no "Approve All" peer to Reject All), the Security section's contents, NavItem/NavRow's separation. Promotion of PQC to a root menu item was proposed by one pass; I'd defer it — the home PqcCard is the route users learned, and the renames above fix the felt confusion without moving anything. Moving learned surfaces without a defect is how the two rolled-back changes happened.

## 6. What NOT to do

- **Do not ship a new "dialog primitive" across nine surfaces at once.** One shared contract, delivered through the R9 migration one dialog per commit. Nine simultaneous blind diffs is the exact shape of last month's rollbacks.
- **Do not change OverlayPanel's default overflow again.** Already tried, already reverted. Footer slot first, opt-in scroll, one consumer per commit, private wrapper deleted in the same commit.
- **Do not tokenize z-index as the stacking fix.** `.card`'s stacking context makes any inside value lose to a `#root` sibling; the fix is a portal/containment decision. And when the scale is written, the non-fullScreen unlock must sit above the approval sheet — both prior reports ordered only "security above wallet."
- **Do not alias `--bg-card` to `--card-bg`.** That is rgba(99,102,241,0.06) — the "fixed" tooltip stays transparent, and the resolvability test would green-light it. Alias to an opaque token.
- **Do not silently origin-scope the pending badge, and do not loosen the approval overlay's fail-closed filter to make the two agree.** The filter fixed a real cross-site exposure; the badge's scope is the explicit product decision (2.5), not a dedup side effect.
- **Do not add an "Approve All", and never migrate ApprovalOverlay onto a dismissable Modal.** The sheet is deliberately non-dismissible; detail-first review is the consent model, not friction to optimize away.
- **Do not move any consent surface (approval, unlock, key export, seed backup, payment) without its named verification pass** — the stacking matrix, the lock-under-modal walk, the keyboard walk. A consent surface that "probably still works" is the one class where this codebase's verify-by-eye protocol is not optional.
- **Do not add Escape per-surface without a top-most-only protocol.** Modal's document-level listener already closes every stacked layer on one keypress; copying those five lines around multiplies the bug.
- **Do not put `autoComplete="current-password"` on vault unlock.** It invites the browser to store the secret the vault exists to guard. `new-password` on creation fields; deliberate `off`, with a comment, on unlock.
- **Do not write the locale test against en's key set.** en also lacks the wizard.type keys; scan source `t()` references and enumerate the dynamic unions.
- **Do not ship the headerRight render without authoring `.headerHelp` in the same commit** — round-2 predicted the unstyled-button half-fix and that is precisely what happened once already.
- **Do not restructure the wizard's steps, the Security section's contents, or the approval grouping, and do not merge NavItem/NavRow** — no defect, learned habits, and the census work reaches consistency without moving anything. Defer the PQC root-menu promotion for the same reason.
- **Do not invest fixes into `src/prompt/` or `src/onboarding/` before the keep-or-delete decision** — several a11y/i18n findings land there and evaporate if the surfaces are (as the reference graph indicates) unreachable.
- Round-2's §6 stands in full: no state or fetch library, no mass useRpc sweep, no `configUpdated` deletion, no dark theme riding the token pass, no `popupInit` mega-RPC, and treat prior reports' framings as hypotheses — the source is the authority.

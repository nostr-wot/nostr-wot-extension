# Experimental local network bridge

Open the extension menu and choose **Experimental → Local network bridge**. A dedicated tab offers Wi-Fi and Bluetooth (BLE). Wi-Fi uses the same trusted local network; Bluetooth uses a nearby phone and a compatible browser. The Bluetooth tile is disabled when Web Bluetooth is unavailable. The user must keep the connection tab and the phone bridge open.

No extension vault setup or unlock is required. When the vault is locked or absent, phone approval creates a separate temporary public-only network account; the encrypted vault stays untouched. With an already unlocked vault, pairing automatically selects an existing matching account or creates a temporary public-only phone account. No public-key import or manual account selection is required. Closing or disconnecting the bridge tab removes its temporary account and permissions and restores the previous selection. If its encrypted vault row is locked, public metadata is removed immediately and encrypted cleanup finishes on unlock. Disconnect also removes the account created for pairing. Existing accounts are never deleted by this cleanup. On the phone open Connections → Local network, select the matching transport and start it. For Wi-Fi, show the pairing code and scan it with the camera icon or paste it. A valid code immediately starts connecting. Camera access is requested only when scanning is opened; frames are decoded locally and never uploaded. Scanning stops after one code, on cancellation, or when the tab is hidden. For Bluetooth, open Pair a computer on the phone and choose the phone through the extension's browser device chooser; no code input, QR or sound is needed. Confirm the number and approve pairing on the phone.

The phone remains the identity signer. The extension generates a separate ephemeral transport key in the tab; neither it nor identity secrets cross the runtime port. The code carries a one-time pairing secret and is cleared from the input after connection. The tab verifies the pinned host transport key, derives fresh encrypted session keys and registers the authenticated returned identity as the selected extension account. Website connection consent and identity-access controls still apply. Every event-signing and encryption request goes directly to the phone before extension request-permission rules run. The phone is the sole approval authority, including app-specific data, destination authentication and follow-list replacement. The extension still validates incoming events and verifies returned signatures; it does not create local approval grants for phone-approved events. Phone permissions apply to the paired computer; website origins are not separately authenticated by this transport. Returned events are checked against the approved content, expected author and valid signature.

This experimental connection supports NIP-07 event signing and NIP-04/NIP-44 encryption/decryption. Unsupported internal publishers, post-quantum signing, Archive authentication and wallet identity operations refuse while phone signing is selected. A disconnected phone never silently falls back to an extension private key or another remote signer. **Disconnect** closes the transport and removes that selection. Public-only accounts then become unable to sign locally, as expected.

Bluetooth uses service `8f93b5a0-6d7c-4d9f-8b01-9d7a6b0e1200`, write-with-response RX `…1201` and notify TX `…1202`. Both BLE and Wi-Fi carry the wallet's `nwlan/2` mutual-signature handshake, mandatory number comparison, per-session HKDF keys and NIP-44 encrypted requests. BLE frames are a four-byte big-endian length followed by UTF-8, capped at 64 KiB. Writes remain serialized and acknowledged. After subscribing, the extension reads optional capability `…1203`: version byte `1` followed by a big-endian uint16 safe write payload size (20–512 bytes). New phones derive that limit from the negotiated ATT MTU; absent, unreadable or invalid capabilities retain 20-byte writes. A failed write closes the stream instead of retrying a potentially delivered fragment. Larger packets reduce round trips without changing encryption or approval. Wi-Fi only accepts literal private/local IP addresses and connects to `/nwlan2`; public destinations and hostnames are rejected. No cloud relay is used for this connection.

A lightweight runtime heartbeat keeps the extension worker available only while connected; it does not scan Bluetooth or poll the phone. Locking or switching accounts, disabling phone signing, losing the radio, or closing the tab cancels the session and outstanding work. Requests time out without automatic retries, since resending a signing request could duplicate an action. The tab's peer key is not persisted; closing it requires pairing again. Browser and mobile OS background restrictions still apply.

## Validation

Run `node --import tsx --test tests/local-bridge-transport.test.ts tests/local-bridge-tab.test.ts` for framing and document lifecycle. The broker suite uses the usual browser mock. `tests/run.sh` includes these checks. For interoperability against a sibling wallet checkout, run `LOCAL_BRIDGE_WALLET_ROOT=/absolute/path/to/wallet node --experimental-default-type=module --import tsx --test tests/local-bridge-wallet-interop.test.mjs`. This exercises the actual wallet session and signer, including approval, signing, encryption and revocation, but does not replace physical Bluetooth testing.

Physical-device acceptance: connect using each transport; approve and reject signing; test both encryption schemes; revoke on the phone; turn Bluetooth off; close the tab; switch extension accounts; lock the vault; confirm failures are visible and local signing does not take over. Native Android compilation and radio tests remain separate release gates. This feature is not enabled or connected automatically.

The bridge tab uses the shared animated topographic background, a raised card for setup and connection controls, the Nostr WoT logo at the top left, and the package version in the footer. The page scrolls naturally on smaller screens.


## Sound pairing availability

Sound is an optional, one-attempt Wi-Fi bootstrap. Click the microphone icon, then **Start listening**, and play the pairing sound on the phone. Opening the page or dialog never activates capture. Audio stays on the computer; the microphone stops after a valid code, error, cancellation, hiding/closing the tab or 30 seconds (including setup). A decoded code advances directly to the existing Wi-Fi handshake and mandatory phone number comparison. The microphone is not needed during the connected session and never restarts automatically, even if the browser remembers permission.

The decoder is built with Emscripten `DYNAMIC_EXECUTION=0` and binary-safe Embind strings. The checked-in module includes its WASM; no scripts or decoder assets are downloaded at runtime and CSP is unchanged. See `third_party/ggwave/PROVENANCE.md` and `scripts/build-sound-decoder.sh` for source and reproducible build instructions. The Chrome package smoke test feeds an independently encoded waveform into the actual microphone/audio worklet path, checks decoded high-bit bytes, automatic Wi-Fi dispatch, CSP, capture shutdown and no restart on reload. Physical speaker/microphone testing is still required for room noise and device volume.

### Mandatory phone comparison for new pairings

New peers send `confirmation: 1` in the signed hello envelope. After verifying the hello, the phone generates a fresh 16-byte random challenge and sends `{v:2,t:"confirm",host,challenge,sig}`. The challenge uses unpadded base64url. The BIP340 signature signs SHA-256 of `nwlan/2/confirm` followed by host key, peer key, hello nonce and challenge, separated by U+001F. The computer verifies against the pinned host key before displaying the comparison code: the first four digest bytes interpreted as unsigned big-endian, modulo 1,000,000, padded to six digits.

The phone offers that number among three shuffled choices and “None match.” The user must choose the number visible on the intended computer. Comparison expires after 45 seconds; cancellation, a wrong choice or disconnect rejects pairing. Only one new peer can be compared at once, with at most five attempts per offer. Remembered signing permissions cannot bypass comparison. Existing paired peers reconnect using their saved public key proof. Old clients without this capability cannot create new pairings; updated clients reject a pairing welcome that skipped comparison. Both applications must be updated together.

QR, pasted links and sound only transfer bootstrap information. Anyone nearby may copy it, but possession alone does not authorize pairing. Users must reject an unsolicited prompt or a number that is absent from their intended computer.

Valid pasted or scanned pairing codes immediately advance to connection. Wi-Fi connects automatically; Bluetooth advances to the native device-selection step, opened by an explicit click to preserve browser user activation. The camera and optional microphone actions are embedded in the code field. Back sits inside the setup card as a neutral gray control and cancels any pending connection.

Bluetooth uses direct discovery: choose the phone in the browser chooser, then choose the displayed six-digit code on the phone. The phone must have Local network → Bluetooth → Pair a computer open. QR and paste are Wi-Fi setup options. Direct discovery commits the peer key and hidden nonce before the phone reveals its challenge; the signed hello reveals the commitment and the signed confirmation must use that exact challenge. No signing session is established without phone confirmation. Older phone builds need updating.

On the phone, Bluetooth’s **Pair a computer** action starts the listener and opens pairing together. A listener running without an open pairing offer refuses discovery; the extension explains how to reopen pairing instead of incorrectly asking for an app update.

A detached network account has an in-memory signing capability tied to the live, authenticated bridge port. Closing the connection, switching accounts, locking/unlocking the vault or restarting the worker invalidates that capability. Temporary public metadata is removed when its bridge port closes. Disconnect removes the temporary metadata and permissions and restores the previous account without unlocking it.

The connected state highlights that the page and phone bridge must stay open. Disconnect uses the shared red danger treatment and closes the live connection and removes any temporary phone account. There is one Disconnect action: it ends phone signing, removes pairing-owned temporary accounts and restores the previous account; existing accounts are retained.

Worker startup also cleans up abandoned pairing-owned temporary accounts from earlier sessions. Cleanup of an older temporary account waits while another phone connection is active, so deleting its vault record cannot interrupt the newer signer. Deferred encrypted removals use independent per-account markers and survive later pairing attempts.

The encrypted RPC may include a `site` containing the exact browser-derived HTTP(S) origin. Updated wallets scope remembered decisions by wallet account and site, independently of Wi-Fi/Bluetooth. A fresh bridge connection must confirm whether to reuse existing choices on the phone before any saved rules apply; Start fresh clears that site's saved rules and authentication grants. This site label is asserted by the paired computer, not independently attested by the phone. One-time approvals are not converted into remembered grants.

Microphone decoding uses a 48 kHz Web Audio graph. The browser resamples other device rates before the worklet; this avoids the ggwave input resampler losing short chunk tails at 44.1 kHz. The packaged Chrome regression simulates a 44.1 kHz default audio context and must still decode the phone-format waveform.

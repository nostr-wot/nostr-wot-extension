# Experimental local network bridge

Open the extension menu and choose **Experimental local network bridge**. A dedicated tab offers Wi-Fi and Bluetooth (BLE). Wi-Fi uses the same trusted local network; Bluetooth uses a nearby phone and a compatible browser. The Bluetooth tile is disabled when Web Bluetooth is unavailable. The user must keep the connection tab and the phone bridge open.

Unlock the extension vault and select the same account as the phone. Importing the phone's public key is sufficient; pairing can copy that public account into the existing unlocked vault without importing identity secrets. On the phone open Connections → Local network, select the matching transport, start it and show the pairing code. Choose **Scan QR code** to read the phone’s QR with the computer camera, or paste the code into the extension tab, then connect. Camera access is requested only when scanning is opened; frames are decoded locally and never uploaded. Scanning stops after one code, on cancellation, or when the tab is hidden. A scanned code is validated before filling the field and never connects automatically. Bluetooth then opens the browser's device chooser. Approve pairing and the identity request on the phone.

The phone remains the identity signer. The extension generates a separate ephemeral transport key in the tab; neither it nor identity secrets cross the runtime port. The code carries a one-time pairing secret and is cleared from the input after connection. The tab verifies the pinned host transport key, derives fresh encrypted session keys and registers the returned identity only when it matches the selected extension account. The existing website permissions still apply, followed by phone-side permissions. Returned events are checked against the approved content, expected author and valid signature.

This experimental connection supports NIP-07 event signing and NIP-04/NIP-44 encryption/decryption. Unsupported internal publishers, post-quantum signing, Archive authentication and wallet identity operations refuse while phone signing is selected. A disconnected phone never silently falls back to an extension private key or another remote signer. **Stop using phone signer** explicitly removes that selection. Public-only accounts then become unable to sign locally, as expected.

Bluetooth uses service `8f93b5a0-6d7c-4d9f-8b01-9d7a6b0e1200`, write-with-response RX `…1201` and notify TX `…1202`. Both BLE and Wi-Fi carry the wallet's `nwlan/2` mutual-signature handshake, pairing MAC, per-session HKDF keys and NIP-44 encrypted requests. BLE frames are a four-byte big-endian length followed by UTF-8, capped at 64 KiB. Writes use serialized 20-byte chunks. Wi-Fi only accepts literal private/local IP addresses and connects to `/nwlan2`; public destinations and hostnames are rejected. No cloud relay is used for this connection.

A lightweight runtime heartbeat keeps the extension worker available only while connected; it does not scan Bluetooth or poll the phone. Locking or switching accounts, disabling phone signing, losing the radio, or closing the tab cancels the session and outstanding work. Requests time out without automatic retries, since resending a signing request could duplicate an action. The tab's peer key is not persisted; closing it requires pairing again. Browser and mobile OS background restrictions still apply.

## Validation

Run `node --import tsx --test tests/local-bridge-transport.test.ts tests/local-bridge-tab.test.ts` for framing and document lifecycle. The broker suite uses the usual browser mock. `tests/run.sh` includes these checks. For interoperability against a sibling wallet checkout, run `LOCAL_BRIDGE_WALLET_ROOT=/absolute/path/to/wallet node --experimental-default-type=module --import tsx --test tests/local-bridge-wallet-interop.test.mjs`. This exercises the actual wallet session and signer, including approval, signing, encryption and revocation, but does not replace physical Bluetooth testing.

Physical-device acceptance: connect using each transport; approve and reject signing; test both encryption schemes; revoke on the phone; turn Bluetooth off; close the tab; switch extension accounts; lock the vault; confirm failures are visible and local signing does not take over. Native Android compilation and radio tests remain separate release gates. This feature is not enabled or connected automatically.

The bridge tab uses the shared animated topographic background, a raised card for setup and connection controls, the Nostr WoT logo at the top left, and the package version in the footer. The page scrolls naturally on smaller screens.


## Experimental sound pairing

Choose **Pair with sound → Start listening**, grant microphone access, then tap **Play pairing sound** on the phone’s pairing screen. The browser decodes audio locally using the bundled ggwave modem; samples are never uploaded or saved. Listening stops after 30 seconds, on a decoded packet, cancellation, tab hiding or navigation. The decoded code fills the same pairing field; click Connect and approve on the phone as usual. Sound only bootstraps pairing and never carries signing requests. Nearby people can hear or record it, so the existing phone approval and pairing-code lifetime remain mandatory. Use the QR or paste fallback in noisy rooms.

The NW/1 binary packet is `4e 57 01 flags`, 32 bytes of host transport public key, 32 bytes of pairing secret, then an optional address and big-endian port. Flags 0 = IPv4 (4 address bytes + 2 port bytes, 74 total), 1 = IPv6 (16 + 2, 86 total), 2 = BLE (no address, 68 total). There are no names, identity keys, or extra addresses. Only the current local address is transmitted; identity is obtained after the authenticated nwlan/2 handshake. The exact length is checked before parsing and the regular pairing validator still rejects public addresses. ggwave’s audible-fast modulation supplies framing and error correction; the authenticated handshake supplies security.

The browser uses the published ggwave 0.4.0 WASM binding and a local AudioWorklet; the wallet uses the native ggwave encoder. Native-to-browser waveform round-trip checks pass for the compact packet. Acoustic reliability through actual speakers and microphones remains a physical-device acceptance check.

### Mandatory phone comparison for new pairings

New peers send `confirmation: 1` in the signed hello envelope. After verifying the hello, the phone generates a fresh 16-byte random challenge and sends `{v:2,t:"confirm",host,challenge,sig}`. The challenge uses unpadded base64url. The BIP340 signature signs SHA-256 of `nwlan/2/confirm` followed by host key, peer key, hello nonce and challenge, separated by U+001F. The computer verifies against the pinned host key before displaying the comparison code: the first four digest bytes interpreted as unsigned big-endian, modulo 1,000,000, padded to six digits.

The phone offers that number among three shuffled choices and “None match.” The user must choose the number visible on the intended computer. Comparison expires after 45 seconds; cancellation, a wrong choice or disconnect rejects pairing. Only one new peer can be compared at once, with at most five attempts per offer. Remembered signing permissions cannot bypass comparison. Existing paired peers reconnect using their saved public key proof. Old clients without this capability cannot create new pairings; updated clients reject a pairing welcome that skipped comparison. Both applications must be updated together.

QR, pasted links and sound only transfer bootstrap information. Anyone nearby may copy it, but possession alone does not authorize pairing. Users must reject an unsolicited prompt or a number that is absent from their intended computer.

# Experimental local network bridge

Open the extension menu and choose **Local network bridge (Experimental)**. A dedicated tab offers Wi-Fi and Bluetooth (BLE). Wi-Fi uses the same trusted local network; Bluetooth uses a nearby phone and a compatible browser. The Bluetooth tile is disabled when Web Bluetooth is unavailable. The user must keep the connection tab and the phone bridge open.

No extension vault setup or unlock is required. When the vault is locked or absent, phone approval creates a separate temporary public-only network account; the encrypted vault stays untouched. With an already unlocked vault, pairing automatically selects an existing matching account or creates a temporary public-only phone account. No public-key import or manual account selection is required. Closing or disconnecting the bridge tab removes its temporary account and permissions and restores the previous selection. If its encrypted vault row is locked, public metadata is removed immediately and encrypted cleanup finishes on unlock. Stop using phone signer also removes the account created for pairing. Existing accounts are never deleted by this cleanup. On the phone open Connections → Local network, select the matching transport and start it. For Wi-Fi, show the pairing code and scan it with the camera icon, paste it, or read it through the microphone icon. A valid code immediately starts connecting. Camera access is requested only when scanning is opened; frames are decoded locally and never uploaded. Scanning stops after one code, on cancellation, or when the tab is hidden. For Bluetooth, open Pair a computer on the phone and choose the phone through the extension's browser device chooser; no code input, QR or sound is needed. Confirm the number and approve pairing on the phone.

The phone remains the identity signer. The extension generates a separate ephemeral transport key in the tab; neither it nor identity secrets cross the runtime port. The code carries a one-time pairing secret and is cleared from the input after connection. The tab verifies the pinned host transport key, derives fresh encrypted session keys and registers the authenticated returned identity as the selected extension account. Website connection consent and explicit extension denials still apply. Ordinary signing and encryption requests go directly to phone-side approval without an additional extension prompt. Destination authentication consent and destructive follow-list confirmation remain extension safety checks. Phone permissions apply to the paired computer; website origins are not separately authenticated by this transport. Returned events are checked against the approved content, expected author and valid signature.

This experimental connection supports NIP-07 event signing and NIP-04/NIP-44 encryption/decryption. Unsupported internal publishers, post-quantum signing, Archive authentication and wallet identity operations refuse while phone signing is selected. A disconnected phone never silently falls back to an extension private key or another remote signer. **Stop using phone signer** explicitly removes that selection. Public-only accounts then become unable to sign locally, as expected.

Bluetooth uses service `8f93b5a0-6d7c-4d9f-8b01-9d7a6b0e1200`, write-with-response RX `…1201` and notify TX `…1202`. Both BLE and Wi-Fi carry the wallet's `nwlan/2` mutual-signature handshake, mandatory number comparison, per-session HKDF keys and NIP-44 encrypted requests. BLE frames are a four-byte big-endian length followed by UTF-8, capped at 64 KiB. Writes use serialized 20-byte chunks. Wi-Fi only accepts literal private/local IP addresses and connects to `/nwlan2`; public destinations and hostnames are rejected. No cloud relay is used for this connection.

A lightweight runtime heartbeat keeps the extension worker available only while connected; it does not scan Bluetooth or poll the phone. Locking or switching accounts, disabling phone signing, losing the radio, or closing the tab cancels the session and outstanding work. Requests time out without automatic retries, since resending a signing request could duplicate an action. The tab's peer key is not persisted; closing it requires pairing again. Browser and mobile OS background restrictions still apply.

## Validation

Run `node --import tsx --test tests/local-bridge-transport.test.ts tests/local-bridge-tab.test.ts` for framing and document lifecycle. The broker suite uses the usual browser mock. `tests/run.sh` includes these checks. For interoperability against a sibling wallet checkout, run `LOCAL_BRIDGE_WALLET_ROOT=/absolute/path/to/wallet node --experimental-default-type=module --import tsx --test tests/local-bridge-wallet-interop.test.mjs`. This exercises the actual wallet session and signer, including approval, signing, encryption and revocation, but does not replace physical Bluetooth testing.

Physical-device acceptance: connect using each transport; approve and reject signing; test both encryption schemes; revoke on the phone; turn Bluetooth off; close the tab; switch extension accounts; lock the vault; confirm failures are visible and local signing does not take over. Native Android compilation and radio tests remain separate release gates. This feature is not enabled or connected automatically.

The bridge tab uses the shared animated topographic background, a raised card for setup and connection controls, the Nostr WoT logo at the top left, and the package version in the footer. The page scrolls naturally on smaller screens.


## Experimental sound pairing

For Wi-Fi, choose the microphone icon → **Start listening**, grant microphone access, wait until the extension displays **Listening**, then tap **Play pairing sound** on the phone’s pairing screen. The browser decodes audio locally using the bundled ggwave modem; samples are never uploaded or saved. The interface shows microphone preparation until the decoder and capture are ready. Listening stops after 30 seconds of ready capture, on a decoded packet, cancellation, tab hiding or navigation. A successfully decoded code starts connecting automatically; confirm the number and approve on the phone. Sound only bootstraps pairing and never carries signing requests. Nearby people can hear or record it, so the existing phone approval and pairing-code lifetime remain mandatory. Use the QR or paste fallback in noisy rooms.

The NW/1 binary packet is `4e 57 01 flags`, 32 bytes of host transport public key, 32 bytes of pairing secret, then an optional address and big-endian port. Flags 0 = IPv4 (4 address bytes + 2 port bytes, 74 total), 1 = IPv6 (16 + 2, 86 total), 2 = BLE (no address, 68 total). There are no names, identity keys, or extra addresses. Only the current local address is transmitted; identity is obtained after the authenticated nwlan/2 handshake. The exact length is checked before parsing and the regular pairing validator still rejects public addresses. ggwave’s audible-fast modulation supplies framing and error correction; the authenticated handshake supplies security.

The browser uses the published ggwave 0.4.0 WASM binding and a local AudioWorklet; the wallet uses the native ggwave encoder. Native-to-browser waveform round-trip checks pass for the compact packet. Acoustic reliability through actual speakers and microphones remains a physical-device acceptance check.

### Mandatory phone comparison for new pairings

New peers send `confirmation: 1` in the signed hello envelope. After verifying the hello, the phone generates a fresh 16-byte random challenge and sends `{v:2,t:"confirm",host,challenge,sig}`. The challenge uses unpadded base64url. The BIP340 signature signs SHA-256 of `nwlan/2/confirm` followed by host key, peer key, hello nonce and challenge, separated by U+001F. The computer verifies against the pinned host key before displaying the comparison code: the first four digest bytes interpreted as unsigned big-endian, modulo 1,000,000, padded to six digits.

The phone offers that number among three shuffled choices and “None match.” The user must choose the number visible on the intended computer. Comparison expires after 45 seconds; cancellation, a wrong choice or disconnect rejects pairing. Only one new peer can be compared at once, with at most five attempts per offer. Remembered signing permissions cannot bypass comparison. Existing paired peers reconnect using their saved public key proof. Old clients without this capability cannot create new pairings; updated clients reject a pairing welcome that skipped comparison. Both applications must be updated together.

QR, pasted links and sound only transfer bootstrap information. Anyone nearby may copy it, but possession alone does not authorize pairing. Users must reject an unsolicited prompt or a number that is absent from their intended computer.

Valid pasted, scanned or sound-decoded pairing codes immediately advance to connection. Wi-Fi connects automatically; Bluetooth advances to the native device-selection step, opened by an explicit click to preserve browser user activation. Camera and sound actions are embedded in the code field. Back sits inside the setup card as a neutral gray control and cancels any pending connection.

Bluetooth uses direct discovery: choose the phone in the browser chooser, then choose the displayed six-digit code on the phone. The phone must have Local network → Bluetooth → Pair a computer open. QR, paste and sound are Wi-Fi setup options. Direct discovery commits the peer key and hidden nonce before the phone reveals its challenge; the signed hello reveals the commitment and the signed confirmation must use that exact challenge. No signing session is established without phone confirmation. Older phone builds need updating.

On the phone, Bluetooth’s **Pair a computer** action starts the listener and opens pairing together. A listener running without an open pairing offer refuses discovery; the extension explains how to reopen pairing instead of incorrectly asking for an app update.

A detached network account has an in-memory signing capability tied to the live, authenticated bridge port. Closing the connection, switching accounts, locking/unlocking the vault or restarting the worker invalidates that capability. Temporary public metadata is removed when its bridge port closes. Stop using phone signer removes the temporary metadata and permissions and restores the previous account without unlocking it.

The connected state highlights that the page and phone bridge must stay open. Disconnect uses the shared red danger treatment and closes the live connection and removes any temporary phone account. Existing accounts remain selected until phone signing is explicitly disabled. Stop using phone signer explains that it removes pairing-owned temporary accounts and restores the previous account; existing accounts are retained.

Worker startup also cleans up abandoned pairing-owned temporary accounts from earlier sessions. Cleanup of an older temporary account waits while another phone connection is active, so deleting its vault record cannot interrupt the newer signer. Deferred encrypted removals use independent per-account markers and survive later pairing attempts.

# Passkey recovery

Passkey creation protects the local vault and prepares recovery without displaying a seed phrase. New credentials use `passkeys.nostrwot.com`. The browser chooses the available passkey provider. PRF support is required; largeBlob support determines whether encrypted recovery can be stored alongside the credential. A passkey's provider and RP must be available on the destination device for recovery to work.

## Using the extension

Choose **Create with passkey** to open the browser’s provider prompt immediately, using `passkeys.nostrwot.com`. New accounts generate a seed internally and use seed recovery for the relay fallback. There is no payload-type selector. Existing private-key, seed and vault payloads are recognized from their authenticated format and retain their type when imported.

Creation asks for user verification once to register the passkey and once more only where needed: a PRF assertion when the provider returns no PRF result at registration, and the recovery write when the provider supports largeBlob. A provider that returns PRF at registration and supports largeBlob therefore needs exactly two prompts. The setup wizard keeps whether accounts existed fixed for the open session (`WizardOverlay`), so the first account appearing mid-setup cannot swap the steps for the seed check and remount them. A remount would abort and repeat the recovery write, or rerun the passkey step and its registration.

Choose **Try other methods → Import or recover account** for a passkey, backup, recovery phrase or private key. **Use a passkey** opens recovery on the default domain. The file picker detects supported vault and Nosskey account backups automatically. **Passkey from another app** asks for the original app or domain because browsers cannot enumerate credentials across domains. No format or key-derivation selector is shown. Domain troubleshooting is collapsed. Creating a new account remains separate; cancellation or failed discovery never offers creation in the recovery screen.

Recovery first reads encrypted data attached to the selected passkey, then queries relays using its public user handle and credential identifier. It decrypts and validates a snapshot without changing storage, displays its accounts, and restores only after confirmation. Cancelling discards the transient proof. A complete vault backup cannot replace a populated vault; external account imports use the existing add-account flow. Changing a domain does not migrate a credential.

Provider storage saves the complete encrypted vault snapshot alongside the passkey when largeBlob is supported and the provider confirms the write. This route does not depend on relays. Relay publication is supplementary and requires the explicit save action; an authentication cancellation never publishes data. The relay save reports accepted destinations and supports retry without replacing the local account. Oversized recovery data is never truncated.

A recovery file is optional after the provider explicitly confirms a successful largeBlob write. Without confirmed provider storage, setup requires downloading and acknowledging the encrypted file, even if relay publication succeeds. Keep it somewhere accessible on another device, such as cloud storage or an email to yourself. The enrolled passkey is still required to decrypt it. Refresh the snapshot after account changes. Local event archives are separate.

For an existing vault, **Settings → Security → Set up passkey unlock** verifies the current password when configured before enrolling the first passkey. This setup is available to existing local-key accounts, including imported nsec accounts. Enrollment preserves existing accounts, imported post-quantum keys and private-cache data; it does not convert remote or watch-only accounts into local signing keys. Complete a confirmed provider write or the recovery-file download before finishing setup. A Passkey settings row at the bottom of Security opens a separate screen. It lists enrolled credentials as compact selectable rows, with their domain below the label and recovery actions below the selected entry. Add another passkey verifies the selected existing credential, then registers a new credential on passkeys.nostrwot.com for the current local account, including when another credential already uses that domain. Existing credentials remain available. The browser excludes enrolled credentials in that domain to prevent replacing one on the same authenticator; users can choose another device or provider. Finish the new credential’s recovery setup with confirmed provider storage or a recovery-file download. There is no Advanced disclosure, payload selector or redundant provider-save action.

## Importing a passkey from another app

Some apps derive the Nostr key from their passkey's PRF output instead of storing it (derived mode, see `nips/passkey/01-passkey-key-modes.md`). **Import or recover account → Use a passkey → Passkey from another app** imports such a key once, as an imported-key account. It is not a sign-in option: afterwards the vault unlocks with its own password or Nostr WoT passkey.

- **Source.** An app from the registry list (`DERIVED_PASSKEY_APPS`, currently `beta.lawallet.io` with parameter set `0x02`), or another HTTPS host whose credential identifies a supported format. Ports, paths, other schemes and Nostr WoT's own passkey domains are refused.
- **Request.** Continue requests the optional host permission for exactly `https://<host>/*`, then one discoverable assertion with that RP ID, required user verification and PRF `eval.first` = `SHA-256(salt_label)`. If no PRF output comes back, one assertion targeted at the selected credential follows; then the PRF-unavailable error.
- **Classification.** Tagged derived handles select their parameter set automatically. Untagged handles are accepted only on a registry host with a known format. Unknown untagged handles are refused instead of guessing. Stored handles are never treated as derived keys; supported Nosskey account backups use the SDK backup reader. If detection changes the initial PRF input, the second assertion is pinned to the selected credential.
- **Key.** `HKDF-SHA256(PRF output, salt = prf_input, info = info_label, 32)`; a zero or out-of-range scalar fails without retry.
- **Confirmation.** The npub is shown and must be acknowledged. Import then uses `onboarding_validateNsec` and the Password step, like a pasted key.
- **Afterwards.** The user is told the original passkey still produces this key and works in that app until removed from the provider. The primary action, **Protect with a Nostr WoT passkey**, opens Passkey settings for the existing enrollment; Later skips it. No passkey or recovery format changes.

PRF output and key bytes are zeroed after derivation, cancel, import and unmount. The hex key sent to the background is a JavaScript string and cannot be erased.

## Recovery payloads

| Format | Restored material | Excluded material |
|---|---|---|
| Provider blobs and recovery files; legacy relay vault snapshots (relay restore only) | All saved vault accounts, including imported nsec accounts and imported post-quantum keys, their stored secrets, credential wrappers and private-cache key | Local event archive, browser settings and permissions outside the vault |
| Relay seed snapshot | The selected account’s mnemonic, name, public key and derivation path | Imported post-quantum keys, separately imported nsec accounts, independent wallet/remote-signer credentials and other seeds |
| Relay single-private-key snapshot | One account's 32-byte signing key, imported as an independent key | Imported post-quantum keys, mnemonic, sibling accounts and other vault state |

Provider blobs and recovery files are full encrypted vault snapshots and preserve imported post-quantum secrets and imported nsec accounts present when saved. New relay snapshots always use the selected account’s seed if present, otherwise its private key; they are not full-vault backups and do not preserve imported post-quantum keys. They never enumerate sibling or unrelated accounts. A seed still cryptographically permits deriving sibling identities; omitting their names and paths does not isolate them from someone who holds that seed. Remote and watch-only accounts have no local secret to export. The selected credential must belong to the current account so its public user handle can locate recovery; preparation and publication reject a different account or an account switch. Legacy snapshots remain readable.

Before publishing a seed snapshot, derive its explicit path or legacy numeric index and verify that it reproduces the account public key; mismatches fail before signing. A seed restores the identities described by its saved derivation paths; it does not discover arbitrary previously used paths or restore every setting attached to those accounts. The single-key scope uses Keytr's existing PRF v1 wire format. Typed seed/vault v4 is a proposal shared through [Keytr implementation PR #38](https://github.com/SovereignTechnology/keytr/pull/38), not a claim that deployed clients already understand it. Other clients need the same RP access and application schema to restore compatible data.

## Cryptography and event contract

Local vault format v2 uses a random AES-256-GCM vault key. Each credential wraps it using its PRF output, HKDF-SHA256 and the existing `nostr-wot/vault/passkey-wrap/v1` context. Legacy wrappers retain their original AAD. Newly recovery-capable wrappers also bind their enrolled recovery author and original scope. New relay exports independently derive the payload type from the selected account’s actual secret material; callers cannot request a whole-vault export. Each wrapper records its RP, allowing old/new/custom credentials to coexist. The top-level record RP matches its first wrapper.

New recovery-capable credentials use the fixed public PRF input UTF-8 `keytr-v1` and put the recovery author's raw public key into the discoverable user handle. PRF output remains secret. A fresh device obtains the public user handle from the authenticator and locates the event without prior account metadata. The selected account signs the recovery event, so relay publication publicly links recovery to that author. The account must remain available for subsequent recovery saves; removing it can require a new recovery enrollment under another signing account.

All recovery events use kind **31777**. The single-key scope uses `d=<credential-base64url>`, `v=1`, `rp`, `algo=aes-256-gcm` and `kdf=hkdf-sha256`. Content is standard base64 of `0x01 | IV(12) | HKDF salt(32) | ciphertext(48)`, totaling 93 bytes. HKDF uses context `keytr nsec encryption v1`; AAD is `UTF8("keytr") | 0x01 | rawCredentialId`. The decrypted key must reproduce the event author and discovered public handle.

Typed scopes use `v=4`, `type=seed|vault`, `schema=com.nostrwot.seed.v1|com.nostrwot.vault.v1` and `credential=<credential-base64url>`, in addition to `rp`, `algo` and `kdf`. Their `d` is `<credential-base64url>:<type>:<schema>`, preventing collision with a single-key event for the same credential. The reference base64url encoding retains padding. Content is standard base64 of `0x04 | IV(12) | HKDF salt(32) | ciphertext(N+16)`. Plaintext is limited to 64 KiB. HKDF uses context `keytr payload encryption v4`; AAD is the UTF-8 compact JSON array `["keytr",4,type,schema,rpId,authorHex,credentialBase64url]`.

The seed schema is UTF-8 JSON `{ version: 1, mnemonic, accounts: [{ name, pubkey, path }] }`. Restore validates the mnemonic, derives every listed path, checks every public key, rejects duplicate identities and requires the recovery author among the derived accounts. The vault schema is UTF-8 JSON using the existing `nostr-wot-passkey-vault` recovery-file format. It is itself encrypted and carries enrolled wrappers; restore validates the selected wrapper, RP, fixed PRF input and author before decrypting/importing that record through the existing guarded restore path.

Ciphertext uses fresh 12-byte IVs and 32-byte HKDF salts with a 16-byte AES-GCM tag. Validators check bounds, signature, event ID, author, kind, unique mandatory tags, credential, RP, algorithms, version and schema. Decryption never guesses whether bytes are a seed or private key. A newer valid snapshot that fails decryption does not silently fall back to an older snapshot.

## Relay transport and lifetime

Creation and fresh-device recovery use the canonical `DEFAULT_RELAYS` bootstrap set; profile relays alone cannot bootstrap a device whose vault has not been restored. The set is defined in `src/constants/relays.ts` and shown before relay save. Queries and publications run concurrently through the existing leased relay pool, with bounded candidates, frames and 10-second per-relay deadlines. The background worker performs encryption, signing and restore; popup code receives only signed ciphertext and public results. Recovery networking does not run on popup startup or ordinary local unlock.

Publication success requires at least one relay acknowledgement of acceptance/already-stored data. The exact prepared signed event is reused during a retry. The short-lived onboarding cache contains signed ciphertext only and expires after five minutes; settings saves prepare a fresh snapshot. Explicit publication rechecks the enrolled credential, author, scope and RP, and the current vault session at the send boundary. Restore lookup itself does not mutate the vault.

## Compatibility and limits

Existing credentials retain their previous RP and random PRF salt. Their file and largeBlob recovery remain readable. Their random user handles do not provide the new relay discovery convention, so enabling relay recovery requires adding a new compatible passkey. A newly enrolled credential does not delete an older credential or silently migrate its RP.

Local largeBlob write confirmation proves that the provider accepted a snapshot, not that another device has received it. Real Apple/Google synchronization must be tested with those providers and devices. Relays may reject large events or discard accepted data. A withholding relay can serve an older snapshot on a fresh device, which has no trusted latest revision. Keep an additional recovery route when availability matters.

Provider blobs, relay events and files are snapshots. Save again after adding/removing accounts, changing keys or changing enrollment. Removing accounts, changing the local unlock method or issuing relay deletion requests cannot erase older copies. Relay metadata reveals the author, RP, credential ID, scope, schema, size and time; relays also observe recovery queries. PRF output and plaintext reach trusted extension code, and JavaScript strings cannot be reliably erased. Never log or persist PRF output or plaintext recovery material.

## Shared SDK

The reusable protocol and provider/transport adapters are implemented in `@nostr-wot/vault` in [nostr-wot-sdk](https://github.com/nostr-wot/nostr-wot-sdk). The extension retains its existing WebCrypto vault implementation and browser lifecycle; the SDK implementation stays portable for native apps. Independent WebCrypto/portable fixtures verify the same wire format. SDK source availability is separate from an npm release; never add unpublished `file:` dependencies to an extension release.


Adding another passkey retains the old credential as an alternate unlock method for the same vault. Multiple credentials may share the same domain and account locator; each credential has its own PRF-derived wrapping key. Recovery setup targets the newly enrolled credential. An encrypted file cannot restore without a credential able to decrypt its snapshot; losing one passkey does not necessarily lose access if another enrolled credential remains.


## Unlock preferences, names and relay availability

After passkey creation or restoration, onboarding reuses the protection screen with 15-minute auto-lock and Use passkey enabled. Confirm keeps those defaults without another biometric request. None hides the switch and requires explicit confirmation; the existing passkey must authorize conversion to no-lock protection. Turning Use passkey off shows the shared password and confirmation fields, verifies the current credential and preserves enrollment while changing the vault’s unlock method. Recovery setup completes before changing local protection. These preferences apply to the whole vault, not just one account.

When multiple passkeys are enrolled, select one in Passkey settings and optionally give it a name. Empty names retain Passkey 1, Passkey 2 and so on. The same labels appear in unlock and recovery selectors. Names are bounded public display metadata, saved only while unlocked; they do not change the provider’s credential name, RP, credential ID, encryption key or relay coordinate. Newly exported vault snapshots include labels; existing copies are not rewritten just to rename a credential.

Opening the selected credential’s relay recovery section checks all configured recovery relays concurrently through the shared relay transport. Recovery events are identified by kind 31777, author public key and the credential/type/schema-derived d tag. Signatures and recovery context are verified before reporting Available. Not found requires a completed relay query with no copy; timeouts and connection failures are Unavailable, and invalid candidate events are Invalid copy. The screen shows snapshot timestamps and the last check time, offers Check, and repeats the lookup after publishing. Availability checks do not decrypt, prompt for biometrics, prove that a snapshot is current, or guarantee future retention. Save recovery to relays publishes a fresh encrypted snapshot after credential verification.

The edit icon appears on hover or keyboard focus (and stays visible on touch screens); it opens a dialog for the optional name. Renaming changes only the public label. Relay status has its own icon and dialog.

Each credential row contains an edit icon and a separate relay-recovery icon. Gray means confirmed provider storage makes relay recovery optional; orange means known file-only recovery; green means at least one relay currently returns a valid signed recovery event. Older credentials without recorded storage evidence stay neutral with an unknown-state tooltip. The relay dialog lists availability and recorded publication acknowledgements separately, with refresh and an add-relay input. Adding a relay validates and saves its WebSocket URL; publication remains explicit. Custom recovery relay choices and acknowledgement timestamps are local metadata. Fresh installations still discover through the default relays; retain a recovery file if relying on custom relays. Provider write capability alone is not treated as a confirmed stored blob.

Discovery requests largeBlob read and the standard recovery PRF input together. A compatible modern credential restores from its blob or relays using that single verification; a legacy salt or missing combined PRF output falls back to a credential-bound second request. The recovered blob must match the selected credential and RP before consuming the PRF result. Transient PRF buffers are cleared after use, errors and cancelled advanced discovery. Ordinary local unlock still uses one verification. Every enrolled passkey shows a recovery icon: older credentials explain missing relay locators, and credentials tied to another account permit checking recovery but require selecting that account before publishing.

During setup, relay publishing is offered alongside the required file download only when provider blob storage is unsupported or fails. It is hidden while a supported provider write is pending and after storage succeeds. For a confirmed provider snapshot, relay publishing is available only through the explicit action in Passkey settings. Relay publication never replaces the required file fallback when provider storage fails.

New credentials default to **Nostr WoT Main** when no passkey is registered locally. Adding another registered passkey offers an optional name before opening the browser prompt, defaulting to **Nostr WoT Account 2**, then 3, and so on. The name is stored as local credential metadata and supplied as WebAuthn user.name and user.displayName. Names do not change the public-key user handle, RP binding or encryption. Local registration counts cannot detect credentials stored only on another installation or provider; a fresh installation can therefore also default to Main. Renaming an existing row changes local metadata, not the provider’s previously saved label.

Recovery setup advances automatically once the provider confirms blob storage, without an optional-download screen or Continue click. File download, acknowledgement and optional relay publication appear only if provider storage is unavailable or fails; they remain hidden during the initial write. Recovery files remain available separately in Passkey settings.

Accounts created with a passkey retain their generated seed and support derived sub-accounts through Create another account. Add Account waits for the seed check before choosing a creation route. A locked seed account remains eligible and the derivation screen requests unlock; lookup failures offer Retry rather than silently creating a new seed. Imported standalone private keys have no seed and cannot derive sub-accounts. Save an updated recovery snapshot after adding accounts.

## Initial auto-lock confirmation

After creating or restoring the first account with a verified passkey, the onboarding auto-lock screen reuses that fresh verification once to confirm passkey, password or None protection. Confirming this screen does not request another WebAuthn operation. The authorization is held only in background memory, expires after five minutes, and is invalidated by locking, switching accounts, reauthentication, or changing protection in Security. If it expires or the background restarts, setup reports that protection must be completed in Security after unlocking. Ordinary Security changes continue to verify the current protection.

## Shared protocol candidate

The external derived-passkey import uses the published `@nostr-wot/identity@1.1.0-next.0` package for handle classification, PRF inputs and key derivation. Extension code retains browser permissions, user confirmation and buffer ownership. This candidate does not enable stored-key or vault imports from other apps; those still require the separate recovery integration and device checks.
